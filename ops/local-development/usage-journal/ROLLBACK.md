# Activation migration and rollback review

This copy supersedes the historical readiness text only for the activation branch. The flag still defaults false. Config true now requires standard mode, sync overflow, explicit positive pending-count/age/relation-byte limits, and the Codex automatic image bridge disabled. The generated Wire provider validates the reviewed schema with a bounded read-only transaction before starting the journal worker/observer or attaching the HTTP admission wrapper; the provider itself runs no DDL. The normal migration runner now embeds additive migration 241 and applies it before service construction, including when the journal flag is false. Other existing application services can initialize earlier, so this is not a claim that every service starts after validation.

The review copy remains outside backend/migrations; its identical DDL body is registered as backend/migrations/241_usage_recovery_journal_v1.sql on this independent r4 repair branch. The runner owns the transaction and migration ledger, with unchanged checksum enforcement and safe failure on object collisions. Applying this migration to production still requires separate authorization. Migration number 241 belongs to the r4 base (head 240); integration onto a newer branch requires collision review and revalidation. It adds one permanent table, PK, two partial indexes (pending and aggregate observation), an immutable-payload function/trigger and a version COMMENT. Lock timeout is 500ms, statement timeout 5s. No business/history/financial backfill, FK change, ACL/role change, financial ledger write, or executable down is included; the standard schema_migrations ledger records the migration checksum. The expected PG18 catalog signature includes types/defaults/CHECKs/indexes/function body, trigger enablement, persistence and RLS flags; mismatches, temp shadow resolution and missing existing-role worker permissions fail closed. A different catalog renderer/version needs review, not an exception or automatic repair.

Enabled admission supports the ordinary HTTP text gateway URLs, with restored JSON body bytes, no nonempty tools/functions, generated audio/image/video/search parameters, known media models (including Gemini URL models) or automatic Codex image bridge. Root/v1/v1beta/Antigravity aliases and gateway upgrades are included in the admission boundary; media/search/async/WS requests receive 503 before auth/scheduling/forwarding. Empty tools and text modalities are allowed. Duplicate JSON keys, malformed JSON and bodies over the configured text/server bound are rejected. New requests outside gateway routes retain the original handler. The release must explicitly approve these compatibility restrictions; it must also verify no preexisting unsupported background jobs/producers or model mappings generate excluded work. This implementation does not make a claim about account-specific mappings or pending media jobs merely from an inbound model name.

For an operator-controlled stop: first freeze external gateway ingress and financial/history cleanup/replay, then inspect tracked HTTP producers and the billing queue. Enabled application cleanup closes admission, calls HTTP Shutdown, waits tracked ordinary HTTP handlers (including sync fallback), stops and waits the real billing pool, and only then cancels/joins journal worker and observer before infrastructure shutdown. Committed journal pending rows need not be discarded or falsely declared empty. Any HTTP/in-flight/billing timeout returns an explicit incomplete-drain error and keeps journal/DB open inside that cleanup call. The inherited main function can still exit after cleanup: this is not a guarantee of process survival on timeout. A cutover/rollback must abort on an incomplete drain; SIGKILL or a short container grace period can still lose an upstream-completed event before its financial+journal transaction commits. Approve and measure that boundary, do not replay debits.

Rollback audit covers every pending/done/quarantined journal row. At a stable cutoff with ingress/producers and relevant cleanup frozen, every journal key must have a matching hot OR archive dedup marker, and neither table may contain a conflicting fingerprint. RollbackReady reads only and refuses missing/conflicting coverage; it never reconstructs markers, histories or charges. The actual r4 repository test demonstrates legacy duplicate replay does not charge the covered event, additive schema/pending snapshots survive, new legacy requests use their original path, and returning to journal code consumes pending snapshots log-only. It is not a full old-server or native-image startup test. Original r4 ignores journal rows, so keep marker coverage frozen/protected throughout rollback, and accept that its best-effort logging loss can return for new legacy requests.

The private synthetic pg_dump/pg_restore rehearsal preserves byte-equivalent financial rows and immutable pending payload, validates the restored schema and then writes the restored pending log without rebilling. It is not a production backup or assurance that restoring an older backup after new live debits is safe. Before an authorized switch, preserve a consistent recoverable database backup/PITR position, application image digest/config and migration ledger; retain all new live money and journal rows during binary rollback. Do not restore a stale pre-switch DB over live financial transactions.

No journal TTL, automatic deletion, done reset, financial replay or destructive down is supplied. Completed keys remain the long-term journal-aware dedup authority. Capacity is an explicit sampled admission contract, not a storage reservation: 5s sampling + 2s read timeout and in-flight work permit overshoot. The worker remains active when the HTTP gate closes so it can drain. Observe reports safe aggregate count/age/bytes/quarantine/error-class/attempt and in-flight fields; failed reads retain previous values but become UNKNOWN/unhealthy. Journal bytes include indexes and completed retained rows. Disk/WAL/replica growth and actual peak body/in-flight memory must be monitored after an approved rollout; finite headroom and a separately approved retention/decommission policy are required operational decisions.

Billing effects + immutable snapshot + result receipt + owner token commit together. Worker uses row-lock SKIP LOCKED, actual single-row usage persistence and all persisted scalar comparison; it never calls Apply/debit. Unknown COMMIT confirms durable receipt/token ownership (billing) or done/hash (worker); uncertain results remain explicit, not automatic financial retries. Permanent PG write errors conditionally quarantine the unchanged snapshot after rollback. Platform caches/notifications/quota side effects after commit remain non-atomic and are never replayed by this worker.

Historical missing logs/amounts remain a separate evidence-limited accounting assessment. Their inability to reconstruct exact past loss does not block acceptance of this new-write repair. No historical repair or financial semantic change is authorized by these local tests. No production stop, migration, backup or image change occurred here; CANCELLED / NO-GO / allow_release=false remain unchanged.
